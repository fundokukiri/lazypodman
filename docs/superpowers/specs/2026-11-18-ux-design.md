# Phase 3 — Events, multi-select, command palette

**Status:** implemented and committed (`b601ed5`, `1969c4c`). This document is the
design record for what shipped; the checklists stay **unverified against a real
Podman** until `TEST.md` sections D–F are run by a human.

Same rules as the earlier phases: Podman-only, rootless first, no UI-goroutine
blocking, new strings only in `pkg/i18n/english.go`, graceful degradation with an
`off:` line rather than a crash, synthetic tests until real output is recorded.

## Intent

Three daily-use gaps, all inside the existing panels (no new panel, no renumbering):

1. See what Podman is doing right now without leaving the TUI (**Events**).
2. Act on several containers at once instead of one by one (**multi-select**).
3. Find an action without memorising its key (**command palette**).

Nothing here needs a new backend endpoint: events go through the existing CLI
client, the other two are pure GUI state.

## 3a. Events tab

**Placement:** last tab of the Containers panel. The Controllers panel already has
Logs/Stats/Health/Env/Config/Top; **Events** is appended so no existing tab moves.

**Data path:** `PodmanClient.StreamPodman(ctx, argv, onLine)` — a generic version of
the kube streaming helper. `StreamKube` now just builds the argv and delegates, so
there is one merged-stdout/stderr scanner implementation.

- Command: `podman events`, no flags. Output is shown **verbatim**, one line per
  read. No JSON parsing: the event schema differs between Podman versions and
  inventing fields is exactly what the roadmap forbids.
- The stream runs as a task bound to the tab context. Switching tab or panel
  cancels the context, `exec.CommandContext` kills the child (`WaitDelay 2s`), so no
  orphan `podman events` process is left behind.
- The header line `# podman events` names the command, so the panel is never
  mistaken for logs.
- If the CLI capability is `Unavailable`, the tab renders `cli off: <reason>` and
  spawns nothing. `CapabilityUnknown` is allowed to try (the CLI check is done at
  startup, so Unknown is rare here).
- Errors while streaming are appended to the buffer as text after the output. A
  cancelled context is not an error and is not shown.

**Non-goals:** filtering by container, pausing the stream, keeping a scrollback
after the tab closes, storing events on disk.

**Known limitation:** on a very busy host the stream is unbounded in memory for as
long as the tab stays open. The mitigation today is that switching away kills the
process; a cap can be added later if it becomes a problem.

## 3b. Multi-select

**State:** `markedContainerIDs map[string]bool` guarded by `markedContainersLock`,
keyed by container ID so a list refresh (which rebuilds `*commands.Container`
values) does not clear the selection. A container that disappears from the list
falls out of the selection naturally.

**Keys:** `space` toggles the mark on the current container. No new panel, no new
mode; the mark is shown as `● ` prefixed to the container name cell, so the table
keeps its column count.

**Action routing:** every lifecycle handler goes through one rule —
`containersToActOn()`:

- no marks → exactly the selected container (old behaviour, unchanged);
- one or more marks → all existing marked containers, in list order.

Applied to `s` stop, `r` restart, `p` pause/unpause, `d` remove menu. Confirmation
texts name the count (`Stop 2 containers?`, `Remove 2 containers?`) so a bulk action
can never be mistaken for a single one. A successful action clears the marks; a
failure keeps them so the user can retry.

**Status line:** `N selected` after a mark, `selection cleared` when the last mark is
removed (10 s flash, same mechanism as healthcheck results).

**Non-goals:** range selection, mark-all, select-by-state, persisting marks across
restarts, multi-select in Images/Volumes/Networks (those panels keep their bulk
command menu).

**Review focus:** a bulk action must never run on an empty set; a stale mark must
not resurrect a removed container; the confirmation count must match the number of
operations actually attempted.

## 3c. Command palette

**Key:** `ctrl+p`, global (works from any panel and from a focused main view). It
opens a normal menu, so `esc` and the existing menu navigation apply.

**Items:** one per visible panel (focus jump), then the kube menu, a healthcheck
run, `podman auto-update`, the Quadlet export, and quit. Implementation calls the **same handlers** as
the keys (`handleGoTo`, `handlePodsKubeMenu`, `handleContainerHealthcheckRun`,
`handleAutoUpdate`, `quit`), so the palette cannot drift from the keybindings, and
there is no second implementation to keep in sync.

Panel entries come from `sidePanelKeys()`, so when pods are hidden the palette has
one fewer entry and never offers a dead panel.

**Non-goals:** fuzzy search, custom commands, dynamic arguments, showing the bound
key next to each item (it is in the help/cheatsheet already).

**Test hook:** `staticKeybindings()` (split out earlier for tests) lets the palette
and binding tests run without constructing panels. Tests assert every item has a
label and an `OnPress`, labels are unique, and `ctrl+p` / `space` / `Q` are bound
exactly once.

## Edge cases and degradation

| Situation | Behaviour |
| --- | --- |
| CLI unavailable | Events tab shows `cli off: <reason>`; palette's auto-update flashes the same; nothing spawns |
| No containers | Multi-select keys do nothing (no selection) |
| Marked container removed by a refresh | Silently dropped from the set |
| Tab switched while streaming | Context cancelled, child killed |
| Palette opened on a hidden panel | That panel is not listed |
